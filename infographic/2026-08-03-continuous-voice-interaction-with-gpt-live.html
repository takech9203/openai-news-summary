Engineering 音声 AI インフラ

GPT-Live: 応答性の高い音声 AI を実現するリアルタイムシステムを 6 か月で構築

全二重音声モデル + 専用メディア高速パスで、人間の会話に期待されるサブ秒の応答性を大規模に実現 🎙️

📅 2026-08-03 | ソース: OpenAI News (Engineering)

概要 — 5 つのキーポイント

OpenAI は第 3 世代音声システム「GPT-Live」を支えるリアルタイムシステムの構築過程を解説するエンジニアリング記事を公開。「音声は流れ続けなければならない」という原則のもと、過去 6 か月間でモデル推論、コンテキスト管理、メディアトランスポートを再構築した。

🔄

全二重 (full-duplex) 音声モデル

ターン検出器 (turn detector) をオーディオパスから排除。音声モデル自体が会話の主導権を持ち、より即時的で自然な会話を実現

⚡

Go 実装の専用メディア高速パス

Python asyncio から Go へ書き直し、フレーム配信の滑らかさが大幅改善。新システムの p95 が旧システムの p50 に匹敵

🧠

GPT-5.5 への非同期委譲

深い推論やツール利用が必要な場合、会話の流れを妨げることなくフロンティアモデルに委譲。「話す」と「考える」を分離する 2 モデルアーキテクチャ

🔀

ハンドオフによる無停止コンテキスト圧縮

モデルインスタンス間のシームレスな切り替え機構により、長時間の通話でもメディアを中断せずコンテキスト圧縮 (compaction) を実行

📡

単一 UDP パケットでセッション開始

WARP と Instant Connect により SDP 交換をクリティカルパスから外し、トランスポートハンドシェイクを集約

ターン制からストリーミングへの移行

Before: 従来の音声アーキテクチャ

  • カスケード型: 音声認識 → LLM → 音声合成が直列実行。レイテンシが増大し、声のトーンやペースの手がかりが失われる
  • speech-to-speech モデル: 音声を直接処理して改善したが、推論開始の判断はターン検出器に依存
  • 検出器が早すぎればユーザーの発話が遮られ、遅すぎれば応答が鈍く感じられる

After: GPT-Live

  • 音声モデル自体が会話の主導権を持つ。音声はモデルに直接流れ込み、モデルから流れ出る
  • 深い推論やツール利用は非同期で実行。フロンティアモデル呼び出しや会話の永続化はライブパスの外で処理
  • システムの主たる役割は途切れのないメディアループの維持

継続的推論を可能にする 3 つの設計上の決定

🛤️ メディアフローとロジックの分離

音声はクライアントと音声モデルの間の専用高速パスを移動。委譲・ツール利用などのアプリケーション処理は非同期 RPC 境界の背後で実行され、遅いツール呼び出しは自身の結果を遅らせてもメディアのフローは停止させない

🐹 Go による再実装

メディアフロントエンドと推論ロジックを Python asyncio 実装から Go で書き直し。フレーム配信の滑らかさが大幅に改善し、新システムの p95 が旧システムの p50 に匹敵する水準に

🌐 WebRTC をトランスポート基盤に採用

低レイテンシメディア向け設計で、パケットロス、クロックドリフト、接続変化があっても動作を継続。パケット遅延時は音声をわずかに引き伸ばしてギャップを防ぎ、その後短時間再生を加速してリアルタイムに追いつく

ステートフルな会話の維持 — ハンドオフ機構

音声セッションは長時間アクティブなまま維持される一方、コンテキストは継続的に増大し、モデルインスタンスは需要に応じて起動・停止する。これに対処するため、モデルインスタンス間のシームレスなハンドオフ機構を構築した。

sequenceDiagram
    participant U as ユーザー
    participant A as モデルインスタンス A
    participant B as モデルインスタンス B (代替)

    U->>A: 音声ストリーム (会話継続中)
    Note over B: ウォームアップ開始
    Note over B: 圧縮済みコンテキストをプリフィル
    U->>A: 会話は中断されない
    U->>B: 並列に推論を実行
    Note over A,B: B の準備完了後に切り替え
    U->>B: メディアを中断せずカットオーバー
  • 並行ウォームアップ: 移行が必要な場合、既存インスタンスと並行して代替インスタンスをウォームアップし、現在のセッションコンテキストをプリフィル。両方に対して並列に推論を実行し、新インスタンスの準備完了時点で切り替える
  • 動的コンテキスト圧縮 (compaction) の課題: 会話が長引くとコンテキストがモデルの上限を超え得るが、圧縮は時間がかかる操作であり、過去のコンテキストを変更するため KV キャッシュ (過去に処理したトークンのアテンションのキーと値) を無効化してしまう
  • 解決策: 圧縮を管理された移行の一種として扱う。元のインスタンスが会話を続ける間にコンテキストを圧縮し、新しいコンテキストで代替インスタンスを準備。メディアを中断せず切り替えられるため、長時間の通話でも必要に応じて圧縮を実行できる

会話をブロックしない委譲

GPT-Live は「話す」ことと深く「考える」ことを分離する 2 モデルアーキテクチャを採用。これを 1 つのシステムのように感じさせるために 2 つの課題を解決した。

① 委譲の高速化

1

推論セッションの事前作成: 音声セッション開始時に、アプリケーションサーバーがフロンティアモデル用の推論セッションを作成し、初期の会話コンテキストをプリフィル。最初の委譲リクエスト前にプロンプト処理を完了させておく

2

セッションアフィニティの維持: 推論セッションを音声会話の間維持し、連続するリクエストに安定したアフィニティを使用。プロンプトキャッシングと組み合わせてレイテンシを改善しつつ、ワーカー障害からの復旧も容易に保つ

3

パラメータ調整: 推論の強度 (reasoning effort)、出力上限、ツールスキーマ、モデルとツール間のラウンドトリップを調整し、会話が有用な結果をより早く受け取れるようにした

② 連続音声からの離散ターンの導出

  • ターンへの分解: ChatGPT の会話 UI や分析・安全性インフラの一部はユーザーとアシスタントのターンを前提とするため、アプリケーションサーバーが重なり合う曖昧な会話を離散的なメッセージに分解する
  • 発話権 (floor) の推定: 部分的な文字起こしとタイミング信号を使ってどの話者が発話権を持つかを推定し、メッセージのキューを構築。最新メッセージは暫定的で、テキスト、タイミング、話者の割り当てはすべて変わり得る
  • 話者の重なりへの対応: ユーザー発話中のアシスタントの短い相槌 ("mm hmm" や "okay" など) は独立したメッセージにせず、実質的な割り込みはメッセージにする
💡 システムは会話の 2 つのビューを維持する。現在の状態の投機的ビュー (UI 表示用) と、発話内容の確定的な記録 (分析パイプラインのログ用) である。

より高速なプロトコルによるセッション開始

応答性はユーザーがボタンをクリックした瞬間から始まる。標準的な WebRTC セッションの開始には多数のプロトコルハンドシェイクとネットワークラウンドトリップが必要で、QUIC のようなラウンドトリップ最小化を重視する後発プロトコル以前の設計であるため、プロトコル間で処理が重複することがあった (例: 各プロトコルが独自の anti-DoS 機構を持つ)。

📜 WARP

WebRTC コミュニティの協力者とともにオープン仕様のセットとして設計。IETF の TSVWG ワーキンググループで提案を進めており、libwebrtc と Pion には既に WARP サポートが追加され、他の WebRTC 実装でも対応が進行中

⚡ Instant Connect

WebRTC 接続前に SDP パラメータを共有するシグナリング交換をクリティカルパスから除去。サーバー容量を予約せず、既存の WebRTC 実装を変更せずにパラメータを事前ネゴシエート。有効なら最初のメディアパケット到着時にサーバーがセッションを実体化し、無効なら進行中の標準シグナリングフローに追加レイテンシなしでフォールバック

🚀 Instant Connect と WARP により、SDP 交換をクリティカルパスから外し、トランスポートハンドシェイクを集約した結果、クライアントは単一の UDP パケットでセッションを開始できるようになった。

実データによる本番環境での安全なテスト

ユーザーへの提供前に、本番の ChatGPT Voice セッションの一部を徐々に増やしながら、既存の Advanced Voice Mode と新システムの両方にルーティングするサイレントテストを実施。Advanced Voice Mode が通常通りユーザーにサービスを提供する一方、シャドウパスは読み取り専用モードで推論を実行し、ユーザーが聞く内容を変えることなく、実際のクライアント、ネットワーク、セッション長、地理的分布にシステムをさらした。

📊 教訓 1: キャパシティは GPU スループットに還元できない

音声セッションは開いたままフレームを送信し続けるため、CPU 側のストリームハンドラ、キュー、ネットワークパスも推論と並行してスケールが必要。実負荷下ではサポートコンポーネントが負荷テストの予測より早く飽和し、推論リクエストの蓄積とレイテンシの複合的悪化を引き起こした。問いを「GPU が何リクエストを処理できるか」から「すべてのフレームをスケジュール通りに保ちながら何セッションを同時に維持できるか」に変更した。

🌍 教訓 2: 地理が第一級の関心事

遠隔のキャパシティへのルーティングは起動時とストリーミング中の複数の時点で遅延を追加する。モデルのロールアウトをリージョンのキャパシティやトラフィックステアリング設定と合わせて検証し、レイテンシを送信元の地理ごとに分解するようにした。

🔍 教訓 3: 現実的なセッションライフサイクルでのみ現れる障害

長時間セッションはメモリと永続化の圧力を露呈し、再接続は圧縮と状態復元を試し、通常のクライアント切断はシャットダウンハンドシェイクの競合を明らかにした。

📈 教訓 4: 可観測性とロールアウト制御の改善

異なるレイテンシ源を混同するメトリクスや、不健全な個別エンジンを隠す集約ダッシュボード、テスト済み構成とデプロイ済み構成のドリフトが見つかった。より粒度の細かいテレメトリ、既知の正常構成に対する検証、段階的ランプ、個別パスの迅速な分離・無効化機能を追加した。

開発者への影響 / ユースケース

🔮 GPT-Live API の予告

この記事のアーキテクチャは今後提供予定の GPT-Live API の基盤となることが明言されており、Realtime API の後継として全二重・低レイテンシの音声体験を開発者が利用できるようになる見込み。

🌐 WARP のオープン仕様化

WARP は IETF TSVWG で標準化が進められており、libwebrtc と Pion に既にサポートが追加されている。WebRTC ベースのリアルタイムアプリケーションを構築する開発者は、この最適化の恩恵を受けられる可能性がある。

🏗️ リアルタイムシステム設計の知見

メディアパスとアプリケーションロジックの分離、Go による低ジッタ実装 (p95 が旧 p50 に匹敵)、ハンドオフによる無停止コンテキスト圧縮、シャドウトラフィックによる本番テストなど、音声 AI に限らずレイテンシ重視のシステム設計全般に応用できるパターンが示されている。

💬 ChatGPT Voice の機能拡張

このアーキテクチャは、ChatGPT デスクトップアプリでのコンピュータ操作やエージェントのコーディネーションといった新機能を支えている。

📝 まとめ

GPT-Live は「音声は流れ続けなければならない」という原則のもとに構築された第 3 世代音声システムである。全二重音声モデルによるターン検出器の排除、Go 実装の専用メディアパス、ハンドオフ機構による無停止のコンテキスト圧縮、GPT-5.5 への非同期委譲、WARP と Instant Connect による単一 UDP パケットでのセッション開始という各レイヤーの最適化により、人間の会話に期待されるサブ秒の応答性を大規模に実現した。このアーキテクチャは ChatGPT Voice のエージェント連携機能を支えており、今後の GPT-Live API の基盤にもなる。
