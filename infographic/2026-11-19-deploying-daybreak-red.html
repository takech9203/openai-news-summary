🛡️ Daybreak Red のデプロイ

監督付きセキュリティ調査のためのリファレンスアーキテクチャ

📅 2026-11-19 | OpenAI News

概要

OpenAI は、サイバーセキュリティ調査向けモデル「Daybreak Red」を安全にデプロイするためのリファレンスアーキテクチャガイドを公開。監督付きセキュリティ調査 (supervised security investigations) のための隔離環境を、アーキテクチャ、安全制御、環境構築、調査の実行と監視という観点から解説している。

🧭

構成より「制御の理解」を重視

リファレンスアーキテクチャは出発点に過ぎない。最も重要な成果は各制御の意図を把握し、自組織の環境で OpenAI のサイバーモデルを安全に実装できるようになること

🏝️

隔離環境での実行

アナリストはワークステーション上の Codex (Coordinator) から調査を指揮。実際のコマンドは分離された使い捨ての Agent VM 上で実行され、ラボのネットワークルールが到達範囲を制限する

🧱

二重の境界による最小権限

Codex サンドボックス (bubblewrap) によるファイル制限と、ネットワーク制御 + 許可リストによる接続先制限を同時に適用する

📊

改変不能な独立ログ

Codex が何を行い、どのリクエストがテスト対象アプリに届いたかを、Codex アカウントの管理外にある独立したログストアが記録。何がいつ起きたかを立証する

⏹️

可視性とガバナンスの維持

モデルにタスク遂行に必要な水準のアクセスを与えつつ、活動への可視性 (visibility) とガバナンスを維持する。Codex の外側からの停止手段も事前に検証する

アーキテクチャの全体像

ガイドが定義する 8 つの構成要素。コンテナを使う場合は、VM と同等のファイルおよびネットワーク制限を強制できることの検証が求められる。

コンポーネント 役割
👤 Analyst 調査を監督する権限を持つ個人。調査の開始、テストのスコープ設定、調査の停止、結果の分析に責任を持つ
🏝️ Isolated environment 環境の論理的分離。本リファレンスでは隔離された VPC 上のホスト型 VM を想定。具体像は各組織のインフラに依存
🎛️ Coordinator アナリストのマシンにローカルインストールされた Codex。リモートホストへの接続管理、結果提示、実行の監督を担う
🖥️ Agent VM 隔離環境内で非管理者ユーザーとして Codex を実行し、分析を実行する。使い捨て (disposable) の VM を前提
🧠 Model inference モデル配信のための OpenAI への接続性。OpenAI モデルは AWS 経由でも利用可能
🚧 Network controls リソースアクセスを制御する論理的なポイント。iptables、ファイアウォール、またはセキュリティグループで実現
🎯 Target 調査を実施する対象となる非本番 (non-prod) アプリケーション
📡 Telemetry Target と Agent VM の外部にあるデータストア。何がいつ起きたかを立証するログを永続化する

安全制御 (Safety controls)

サイバーモデルのデプロイには複数層の安全制御が必要。本設計は OpenAI が推奨するサイバー業務向け構成に従っている。

📐 スコープ定義

対象 (target)、許可されるアクション、調査ウィンドウ、停止ポイントを定義。必要な証拠、匿名アクセスか専用アカウントかを事前に決定し、サインインする場合はアカウントを調査に必要なロールとリソースに限定する

🖥️ VM システム制御

Codex は専用の非管理者アカウントで実行し、サンドボックスで読み書き範囲を制限。書き込み可能なワークスペースは必要時のみ付与。秘密鍵、デプロイ用クレデンシャル、ホスト管理ソケットは手の届かない場所に置く

🌐 ネットワークアクセス制御

Codex のネットワークプロキシで接続先を絞る。VM が 3 つのステージングアプリに到達可能でも、許可リストはスコープ内の 1 つだけを許可。ブラウザ、コネクタ、MCP ツールを有効化する場合は個別にアクセスを確認する

👀 機密アクションのレビュー

承認を要し Auto-review の対象となるアクションは、別のレビュアーが続行可否を判断。新しい対象やアカウント、スコープ外アクションの場合は一時停止し、アナリストが権限を確認してから続行する

📡 テレメトリと制御

Codex のツール活動、対象のリクエストログ、アプリケーションのサインインイベントを、Codex アカウントの管理外にあるログストアに保持する

1.指揮と実行の分離: アナリストは Coordinator を介してのみ調査を指揮し、コマンド実行は隔離環境内の Agent VM に閉じ込められる
2.二重の境界: Sandbox と Network Controls が、ファイルアクセスと到達先を同時に絞る
3.外部テレメトリ: Telemetry は Target と Agent VM の外部に置かれ、Codex アカウントから書き換えられない。さらに Codex の外側から VM を停止できる経路 (破線) が監視喪失時の最終的な制御として確保される

環境構築 (Building the environment)

必要なものは、非本番の対象、Codex を入れたワークステーション、ラボ VM、独立したログストア。対象は合成データ (synthetic data) で準備し、サインインが必要な場合は専用のテストアカウントを作成する。

1

Agent VM の準備

隔離ラボ内に Linux VM を作成し、専用の非管理者アカウントと Codex 用の作業ディレクトリを用意。Codex と調査ツールをインストールし、bubblewrap を導入してコマンドをサンドボックス内で実行。調査開始前にサンドボックスの動作を検証する。リスクの高い調査では新規の VM とラボを使用。ラボは承認済みテストアプリと、サインイン・モデルアクセス・ログエクスポートに必要なサービスのみに到達可能とし、ネットワーク制御は Codex アカウントが変更できないものを使う。

2

ワークステーションからの接続

Agent VM のホストエイリアスと専用アカウントを ~/.ssh/config に追加して SSH 接続。専用ユーザーとして codex login を実行し、Daybreak Red の利用が承認された ChatGPT アカウントとワークスペースでサインイン (ブラウザがない場合はデバイスコード、API アクセスの場合は承認済みプロジェクトのキー)。Codex の Settings → Connections で SSH ホストを追加し、Add new project でワークスペースフォルダを選択。接続確認として、ホスト名と作業ディレクトリを報告させて SSH で見た値と比較する。

3

Codex の権限設定

Agent VM 上の ~/.codex/config.toml を編集する。

  • ファイルとフォルダ: 権限プロファイル内で読み書きできるワークスペースパスを指定
  • ネットワークアクセス: [permissions.<name>.network] で enabled = true。承認済みドメインを列挙し network_proxy = true。ラボ側の制限は維持
  • 承認: approval_policy = "on-request" と approvals_reviewer = "auto_review"。サンドボックスは有効のまま
  • 必須設定: 管理者が requirements.toml に配置し、VM アカウントが上書きできないようにする

プロファイルの有効化は default_permissions にプロファイル名を設定し、リモートチャットの権限メニューから選択。プリフライト実行前に選択内容を確認する。

4

対象アクセスとロギングの設定

対象アプリへのサインインには専用テストアカウントと必要最小限の権限を使用。短命 (short-lived) のクレデンシャルを使い、再利用可能なシークレットは Codex の手の届かない場所に置く。Codex のログは [otel] で OpenTelemetry ログエクスポーターを設定し、OTLP エンドポイントまたは Collector 経由で送信。対象アプリのリクエストログとサインインイベントも同じストアへ送り、Codex アカウントが保存済みレコードを変更・削除できないようにする。

調査の実行と監視

✈️ プリフライトの実行

調査本番と同じ承認済みモデル・同じ権限プロファイルを使い、制御が実際に効いているかを事前検証。検証用に、許可リスト外で自分が管理している URL と、ワークスペース外の使い捨てパスを用意する。

✔ワークスペース: ワークスペース内への書き込みが成功し、ワークスペース外への書き込みがブロックされること
✔ネットワーク: 承認済みのヘルスチェックリクエストが成功し、許可リスト外へのリクエストがブロックされること
✔ログ: 独立したログ側に、成功したツール実行イベント (codex.tool_result) と承認済みヘルスチェックリクエストが記録されていること

📝 調査の記述

プリフライト通過後、対象、調査する問い、使用するテスト ID または匿名アクセス、許可されるアクション、除外する系やデータ、収集する証拠、終了時刻と停止条件を明示したブリーフをリモートの Codex プロジェクトへ送る。必要なルートやアカウントがあれば具体的に指定する。

🚦 実行の監督: 3 つの判断

▶️ Continue (続行)

合意済みスコープ内の定型的な作業はそのまま進めさせる

⏸️ Pause (一時停止)

別のホストに到達した、実際のユーザーデータに遭遇した、より広い権限を要求した場合は、続行前に何が起きたかを確認する

⏹️ Stop (停止)

必要な制御またはその監視が機能しなくなった場合は実行を終了する

🛑 キルスイッチの事前検証: 初回実行の前に、Codex の外側から Agent VM を停止する、あるいは対象へのアクセスを遮断できることを検証しておく。監視を失った場合、直ちに停止する必要がある場合、実行が停止したと確認できない場合には、その制御を使う。

🏁 調査の終了: 4 ステップ

1

停止の指示

リモートチャットで停止を指示。何が停止したかと、クリーンアップが必要なジョブやファイルを報告させる

2

停止の検証

Agent VM のバックグラウンドジョブと対象のログを確認し、双方が停止したことを検証する

3

セッションの終了

ワークステーションからリモートの Codex セッションを終了する

4

クレデンシャルの失効

一時的なクレデンシャルを失効させる

オプションのウォークスルーについて

ガイド末尾には、使い捨ての Gitea インスタンスを対象に、本リファレンスアーキテクチャの設計を実際の既知 CVE の検証へ適用するオプションのウォークスルーが収録されている。本インフォグラフィックでは防御的な運用設計に焦点を当てるため、具体的な検証手順やプロンプトは扱わない (詳細は公式ガイド PDF を参照)。そこでも適用される原則は本文と一貫している。

✔対象ホストと Agent VM 以外は対象アプリのポートに到達できないことの確認
✔セットアップ用クレデンシャルをエージェントの手の届かない場所に置くこと
✔合成データによるフィクスチャの利用
✔レート・試行回数・フェーズ時間の明示的な上限設定
✔クレデンシャルや生レスポンスを除いた形での結果報告
✔終了後のトークン失効とトークンを含むファイルの削除

ユースケース / 開発者への影響

🏗️ 高権限エージェント運用の基準設計として

Coordinator と Agent を分離し、実行を使い捨ての非管理者 VM に閉じ込める構成は、Daybreak Red に限らずエージェントに高権限の作業をさせる場合の一般的な設計指針として参照できる。「VM は 3 つのステージングアプリに到達できても許可リストは 1 つだけ」という二重の境界は、権限の最小化を多層で実装する具体的なモデルを提供する。ブラウザ、コネクタ、MCP ツールを追加するたびにネットワークアクセスを個別検証する必要がある点も実務的な注意点である。

🔍 監査・コンプライアンス対応の参照モデルとして

requirements.toml による管理者側の必須設定、Codex アカウントが変更できないネットワーク制御、Codex アカウントの管理外にあるログストアという 3 点は、エージェントが自らの制約や監査証跡を改変できない構造を要求する。さらにプリフライトで「ワークスペース外への書き込みと許可リスト外へのリクエストが実際にブロックされ、それが独立したログに記録される」ことまで確認する手順は、「設定したつもりで動いていなかった」という失敗モードを運用手順として潰す設計になっている。

🧪 安全なセキュリティ検証環境の構築に

対象は非本番アプリ、データは合成データ、サインインは専用テストアカウントと短命クレデンシャルが前提。実際のユーザーデータに遭遇した時点で一時停止する判断基準が明示され、初回実行前に Codex の外側から VM を停止、または対象へのアクセスを遮断できることを検証しておくというキルスイッチの考え方は、エージェント運用一般に適用できる。

まとめ

本ガイドの中核は 3 つの構造である。(1) ワークステーション上の Coordinator と隔離環境内の Agent VM の分離、(2) Codex サンドボックスとネットワーク制御による二重の境界、(3) Codex アカウントの管理外に置かれたテレメトリ。

運用面では、スコープ定義 → プリフライトによる制御の実効性検証 → Continue / Pause / Stop の判断基準に基づく監督 → 停止・セッション終了・クレデンシャル失効という終了手順まで、ライフサイクル全体が規定されている。

OpenAI が繰り返し述べているように、このアーキテクチャは出発点であり、最も重要な成果は構成のコピーではなく制御の理解である。モデルに必要な水準のアクセスを与えながら可視性とガバナンスを失わないという原則は、高権限のエージェントを運用するあらゆる場面に適用できる。
