Qodo が Codex プラグインで AI コードレビューに組織コンテキストを組み込む

「コーディングエージェントの最良の友」が、PR 前にリポジトリ横断の P0 バグを検出

📅 2026-11-02 | ソース: OpenAI News

概要

OpenAI は、コードレビューとソフトウェア品質の AI ツールを開発するスタートアップ Qodo の事例を公開した。共同創業者兼 CEO の Itamar Friedman 氏は自社を「コーディングエージェントの最良の友 (the coding agent's best friend)」と表現する。

🔌

Codex マーケットプレイスでプラグイン公開

コードベースのナレッジ、組織のルール、独立したレビューを Codex のコーディングセッションに直接持ち込む。

🚨

PR 前にリポジトリ横断の P0 バグを検出

開発者がプルリクエストを開く前に、リポジトリ横断の P0 (最優先度) バグを検出できるようにする。

🧠

組織ナレッジでコーディングエージェントを支援

コーディングエージェントが変更するコードを正しく理解できるように、組織のナレッジを提供することが Qodo の使命。

🤖

GPT-6 Astra を含む OpenAI モデルを活用

エンジニアリングナレッジの収集、コードレビュー、ソフトウェア品質のモニタリングに OpenAI モデルを使用。

☯️

コーディングとレビューを「陰と陽」として対峙

エージェント同士が議論し、合意に至らなかった問題のみを人間のレビューに委ねるビジョン。

主な内容

1リポジトリ横断で P0 バグを発見する

顧客環境は 10,000 以上のリポジトリに及ぶことがあり、ローカルなコード変更がそれ自体は正しく見えても、下流のサービスを壊す可能性がある。Friedman 氏は「Codex はローカルなタスクを効率的に完遂することに非常に優れている」と述べる一方、こうした環境では単一リポジトリの視点だけでは不十分だと指摘する。

Qodo のプラグインは、Agentic Toolbox を通じてコードベースのナレッジ、組織のルール、独立したレビューへのアクセスを Codex に提供する。このコンテキストにより、Codex は異なる Git プロバイダーでホストされているリポジトリや、Kafka で接続されたサービスを含む、リポジトリをまたいだ依存関係を考慮できるようになる。

💬 Friedman 氏:「Qodo がその接続を作り、Codex がソフトウェア全体を見渡して P0 バグを見逃さないよう支援する」

2レビューの自動化と人間の判断の両立

ワークフローでは、Codex のコーディング作業と Qodo の独立レビューの間のハンドオフが自動化されている。AI Developer Relations Lead の Nnenna Ndukwe 氏によれば、開発者はこのワークフローを使い、Codex 上の GPT-6 モデルで機能開発や技術的負債の解消に取り組んでいる。

STEP 1

コンテキスト取得

Codex がコードを書き始める前に、プラグインを通じて関連するコードベースのルール、PR の履歴やパターンを取得

STEP 2

コード変更

Codex が組織コンテキストを踏まえて変更を加える

STEP 3

独立レビュー

Qodo が変更をレビューし、同一セッション内で Codex に直接フィードバック

STEP 4

PR 作成

開発者はレビュー済みの変更でプルリクエストを開く

Friedman 氏は、コーディングエージェントとレビューエージェントを「陰と陽 (yin and yang)」に例える。それぞれの役割には固有のセットアップとコンテキストが必要で、複数のエージェントが関与することもある。

🔍

同氏のビジョンは、エージェント同士が発見事項を議論し、「合意に至らなかったものだけを表面化」させて人間のレビューに委ねること。開発者はプランナーおよびレビュアーとなり、未解決の問題をエージェントの議論、コンテキスト、過去の開発者の判断とともに検査できるようになる。

💬 Friedman 氏:「それが信頼を生む方法だ」 / Ndukwe 氏:「プロセス全体がより効率的になり、私たちは自分の専門性の最良の部分を活かせる」

3Codex を日常業務で活用する

Qodo 社内では、Ndukwe 氏が GPT-6 Astra の Extra High および Ultra effort 設定を、自動化された開発ワークフローやナレッジワークに活用している。

  • 📊 1 週間の成果と、次に注力・改善すべき領域をレポートするよう Codex をスケジュール実行
  • 🔎 ソーシャルプラットフォーム上のエージェンティックエンジニアリングに関する議論をリサーチし、開発者向けコンテンツのアイデアを提案
  • 🛠️ 自身のコード変更を分析させ、作成・改良すべきエージェントスキルを提案

4Decisions API で適用すべきコーディングルールを選択する

Friedman 氏は、OpenAI が最近リリースした Decisions API を使い、開発の各段階でどのルールとエージェントスキルを適用するかを、すべて言語モデルに頼るのではなく選択させる機会があると見ている。たとえば 200 のルールのうちどれをチェックすべきかを Decisions API が選択し、その後に言語モデルが関連するルールについて推論するという構成により、選択を高速かつ低コストにしながらレビューの品質を向上できるという。

💬 Friedman 氏:「Decisions API は、プロセスにより多くの信頼をもたらす計り知れない機会だ」

5顧客が所有できる「ソフトウェアファクトリー」の構築

Qodo のアプローチは「人工知能の最良の側面と、伝統的なソフトウェアエンジニアリングおよびスクリプティングの最良の側面」を組み合わせたものだと Ndukwe 氏は語る。企業のナレッジがコーディングエージェントを導き、独立したレビューがその成果を検証し、残った問いを人間の専門性が解決する。

これは Friedman 氏が「ソフトウェアファクトリー」と呼ぶものの基盤となる。顧客自身が組み立てて所有できるシステムであり、コーディングエージェントとレビューエージェントを、本番環境でソフトウェアがどう変化するかの理解とともに統合するものである。

📏 組織ルールの取得

コーディング前に関連するコードベースルール、PR 履歴・パターンを Codex に提供する。

開発者への影響

✅ PR 前の品質ゲート

プルリクエストを開く前の同一 Codex セッション内でレビュー結果が返るため、レビューサイクルの手戻りを削減できる。

🛡️ リポジトリ横断の安全性

ローカルには正しく見える変更が下流サービスを壊すリスクを、クロスリポジトリの依存関係コンテキストによって低減できる。

📐 組織標準の自動適用

コーディング規約や PR パターンなどの組織ナレッジがエージェントのコーディング段階から反映される。

🔄 役割の変化

開発者はコードの詳細な検査者から、エージェント間で合意に至らなかった問題を裁定するプランナー・レビュアーへと役割が移行していく。

🌐 エコシステムの示唆

Codex マーケットプレイスのプラグインとして提供されており、サードパーティツールを Codex セッションに統合するパターンの参考になる。

まとめ

Qodo は、Codex マーケットプレイスのプラグインを通じて、組織のナレッジ・コーディング標準・独立レビューを Codex のコーディングセッションに統合した。これにより、10,000 以上のリポジトリに及ぶ環境でも、プルリクエスト前にリポジトリ横断の P0 バグを検出できる。コーディングエージェントとレビューエージェントを「陰と陽」として対峙させ、合意できない問題のみを人間に委ねるというビジョンは、Decisions API によるルール選択の高速化・低コスト化とあわせて、顧客が所有できる「ソフトウェアファクトリー」の構想へとつながっている。コーディングエージェントの出力品質を組織コンテキストで高めるアプローチの代表的な事例といえる。
