API 更新

プラットフォーム設定でプロジェクトごとのサービスティア選択が可能に

プロジェクト単位・組織単位の 2 階層でサービスティアの利用ポリシーを統制。許可されていないティアのリクエストは 400 invalid_request_error で拒否

📅 2026-10-21 | ソース: OpenAI API Changelog (Feature)

概要

🎛️

プロジェクトごとのサービスティア選択

プラットフォーム設定で、プロジェクトが使用できるサービスティアを選択可能に。Changelog では「You can now choose which service tiers projects can use in Platform settings」と説明されている。

🏢

組織設定で全プロジェクトを一括制限

「Organization settings can restrict service tiers for all projects」として、組織設定で全プロジェクトに対して一括でティアを制限することも可能になった。

🛡️

2 階層のポリシー統制

組織管理者はプロジェクト単位・組織単位の 2 階層でサービスティアの利用ポリシーを統制できる。組織設定が上位ポリシーとして機能し、プロジェクト設定はその範囲内でのみ選択できる。

🚫

不許可ティアは 400 エラーで拒否

許可されていないティアを指定したリクエストは 400 invalid_request_error で拒否される。意図しないティアの利用によるコストや挙動のばらつきを設定レベルで防止できる。

主な内容

📁 プロジェクト単位のティア選択

プラットフォーム設定 (プロジェクト設定) で、そのプロジェクトが使用できるサービスティアを選択可能。制限対象は default、flex、priority の各ティア。fast ティアは priority として評価され、Scale Tier はこのプロジェクトポリシーの対象外。

🏛️ 組織単位の一括制限

組織設定では全プロジェクトに対してサービスティアを制限できる。公式ドキュメントには「Projects cannot enable tiers blocked by the organization」と明記されており、組織でブロックされたティアをプロジェクト側で有効化することはできない。

⛔ 制限時の API の挙動

許可されていないティアがリクエスト・解決された場合、ステータス 400 (Invalid service_tier argument)、エラー種別 invalid_request_error (error.param は service_tier) が返る。service_tier 省略時や auto 指定時も、解決先のティアが不許可なら同じエラーになる。

📋 ティアごとの制限対象

サービスティア プロジェクトポリシーでの扱い
default 制限対象
flex 制限対象
priority 制限対象
fast priority として評価される
Scale Tier プロジェクトポリシーの対象外 (別途管理が必要)

アーキテクチャ

技術的な詳細

⚙️ service_tier パラメータとの関係

service_tier は API リクエストで処理ティアを指定するパラメータで、たとえば Flex processing を使う場合は service_tier="flex" を指定する。パラメータを省略した場合はプロジェクトのデフォルトモードが使用される。

Python flex ティアを指定した Responses API 呼び出し例 
from openai import OpenAI

client = OpenAI()

# プロジェクトで flex ティアが許可されている場合のみ成功する
response = client.with_options(timeout=900.0).responses.create(
    model="gpt-6-astra",
    service_tier="flex",
    input="Classify this support ticket...",
)

プロジェクトで flex が許可されていない場合、上記のリクエストは 400 invalid_request_error で失敗する。

🚨 400 invalid_request_error の挙動

エラーレスポンスの内容

  • ステータス: 400 - Invalid service_tier argument
  • エラー種別: invalid_request_error (error.param は service_tier)
  • メッセージ: "Invalid service_tier argument: The requested service tier is not allowed for this project."
  • service_tier を省略した場合や auto を指定した場合でも、解決先のティアがプロジェクトで許可されていなければ同じエラーが返る ("Requests that omit service_tier or set it to auto can also return this error")

🔧 エラー発生時の解決手順

  1. プロジェクト設定と組織設定の両方で許可されているティアを確認する (組織でブロックされたティアはプロジェクト側で有効化できない)
  2. service_tier にプロジェクトで許可されているティアを指定する ("Set service_tier to a tier allowed for the project, or update the allowed service tiers in project settings")
  3. auto 指定または省略時は、解決されるティアが許可されるようプロジェクト設定を更新する

ユースケース / 開発者への影響

💰 コストガバナンスの強化

高コストの priority (および priority として評価される fast) や、挙動の異なる flex の利用をプロジェクト単位で制限できるため、本番・開発などプロジェクトの性質に応じたティア統制が可能になる。

⚠️ 既存リクエストへの影響に注意

service_tier を省略または auto 指定している既存のアプリケーションでも、解決先のティアが許可されていなければ 400 エラーが発生する。制限を導入する際は既存ワークロードのティア利用状況の確認が必要。

🧰 エラーハンドリングの追加

invalid_request_error (error.param: service_tier) を考慮したエラーハンドリングを実装し、エラー発生時はプロジェクト設定・組織設定の確認を促す運用が推奨される。

📝 管理者が押さえるべきポイント

  • 2 階層ポリシーの理解: 組織設定が上位ポリシーとして機能し、プロジェクト側では組織がブロックしたティアを有効化できない。管理者は組織・プロジェクトの両設定を一貫して管理する必要がある
  • Scale Tier は対象外: Scale Tier はこのプロジェクトポリシーの対象外のため、別途管理が必要

まとめ

プラットフォーム設定でプロジェクトごとに使用可能なサービスティア (default / flex / priority) を選択できるようになり、組織設定では全プロジェクトへの一括制限も可能になった。組織でブロックされたティアはプロジェクト側で有効化できず、許可されていないティアへのリクエストは 400 invalid_request_error (param: service_tier) で拒否される。auto 指定や省略時のリクエストも解決先のティアが不許可ならエラーになるため、制限を導入する際は既存ワークロードへの影響確認とエラーハンドリングの整備が重要となる。
