Responses API で 12 時間プロンプトキャッシュが選択可能に

共有インストラクション、ツール定義、コンテキストをより長くキャッシュに保持。間欠的なワークロードでも低価格のキャッシュ入力料金を活用可能に

📅 2026-10-20 | ソース: OpenAI API Changelog (Feature · API: v1/responses)

概要

⏰

12 時間のキャッシュ保持期間が選択可能に

Responses API で 12 時間のプロンプトキャッシュ保持期間を選択できるようになった。「長い間隔を挟んで再利用される安定したプレフィックス」向けで、12 時間は「最低保持期間」であり削除期限ではない。

⚙️

prompt_cache_options.ttl で指定

GPT-5.6 以降のモデルで、リクエスト単位に "30m" (デフォルト) または "12h" を指定。ブレークポイント prompt_cache_breakpoint.ttl で部分ごとの上書きも可能。

💰

書き込みは入力単価の 2.5 倍、読み取りは 0.1 倍

12 時間キャッシュの書き込みコストは未キャッシュ入力トークン価格の 2.5 倍 (30 分保持は 1.25 倍)。読み取りは保持期間に関係なく 0.1 倍 (GPT-6.1 Sol は 0.05 倍)。

🔄

30 分と 12 時間の使い分けでコスト最適化

30 分保持は「頻繁に再利用される会話・エージェントの文脈」向け、12 時間保持は「長い間隔を挟んで再利用される安定したプレフィックス」向け。再利用パターンに応じた使い分けが可能。

📊

保持期間別の使用量レポート

レスポンスの input_tokens_details.cache_write_tokens_details で、書き込みトークンが ttl_30m_tokens と ttl_12h_tokens に分解され、保持期間別のコストをモニタリングできる。

主要機能

⏳ 12 時間 TTL オプション

共有インストラクション、ツール定義、コンテキストを 12 時間以上キャッシュに保持。リクエストの間隔が数時間空くワークロードでも、低価格のキャッシュ入力料金の恩恵を受けられる。12 時間保持は Responses API のみの提供。

🛠️ 指定方法

Responses API のリクエストに prompt_cache_options.ttl を指定。値は "30m" (デフォルト) または "12h"。非対応の値は 400 invalid_request_error が返る。

📍 ブレークポイントで上書き

リクエスト単位の設定を、コンテンツ内の個別ブレークポイント prompt_cache_breakpoint.ttl で上書き可能。明示ブレークポイントは 1 リクエストあたり最大 4 つの書き込みスロット (暗黙モード併用時は暗黙が 1 枠を消費)。

🤖 対象モデルと前提条件

ttl オプションは GPT-5.6 以降のモデルで対応。最小キャッシュ可能トークン数は可視入力トークン 1,024 (非表示システムトークンは含まない)。キャッシュは KV テンソルを保存する方式で、組織間やリージョン境界を越えた共有は不可。

🔁 タイマーの挙動の違い

30 分キャッシュへの読み取りは有効期限を少なくとも読み取り後 30 分に更新する。一方、12 時間キャッシュのタイマーは読み取りで再始動せず、追加の書き込み課金も発生しない。

🔀 旧パラメータからの移行

旧モデルの prompt_cache_retention (値は in_memory または 24h) には 12 時間設定はなく、ドキュメントでは prompt_cache_options.ttl への置き換えが移行時の指針として示されている。

💡 料金に関する注意点

  • 書き込み料金は通常入力への加算サーチャージではなく、総額レート ("These are total write rates, not surcharges on top of ordinary input")
  • 30 分カバレッジを 12 時間に格上げすると、該当トークン分の 12 時間書き込みが新たに課金される (旧書き込み分のクレジットはなし)
  • 1 リクエスト内で各トークンは、それをカバーする書き込みのうち最長の保持期間で一度だけ課金される

コードサンプル

公式ドキュメントに掲載されているリクエスト例。リクエスト全体のデフォルト TTL を 30m とし、共有インストラクション部分のみブレークポイントで 12h に上書きしている。

JSON Responses API リクエスト例 (TTL のブレークポイント上書き) 
{
  "model": "gpt-6.1-sol",
  "prompt_cache_options": { "mode": "explicit", "ttl": "30m" },
  "input": [
    {
      "role": "developer",
      "content": [{
        "type": "input_text",
        "text": "Shared instructions and reference material reused throughout the day...",
        "prompt_cache_breakpoint": { "mode": "explicit", "ttl": "12h" }
      }]
    },
    {
      "role": "user",
      "content": [
        {
          "type": "input_text",
          "text": "Session context reused over the next few minutes...",
          "prompt_cache_breakpoint": { "mode": "explicit" }
        },
        { "type": "input_text", "text": "The current question, which does not need a cache write..." }
      ]
    }
  ]
}

📊 使用量レポート

  • レスポンスの input_tokens_details.cache_write_tokens_details で、書き込みトークンが ttl_30m_tokens と ttl_12h_tokens に分解される。両者は重複せず、合計が cache_write_tokens と一致する
  • コスト計算では、30 分書き込みに入力単価 × 1.25、12 時間書き込みに × 2.5、cached_tokens にはキャッシュ入力単価を適用する

ユースケース / 開発者への影響

🕐 間欠的なワークロードのコスト削減

数時間おきに実行されるバッチ処理、カスタマーサポート、日中に断続的に利用される社内ツールなどで、リクエスト間隔が 30 分を超えてもキャッシュヒット (読み取り 0.1 倍) を維持できる。

🧮 コスト設計の見直し

12 時間書き込みは入力単価の 2.5 倍のため、再利用頻度が低いプレフィックスに適用すると逆にコスト増になり得る。安定した共有プレフィックスにのみ 12h を適用し、セッション文脈は 30m に留める設計が有効。

🔀 移行と使用量の可視化

旧モデルの prompt_cache_retention から prompt_cache_options.ttl への置き換えがドキュメントで案内されており、GPT-5.6 以降への移行時はパラメータの変更が必要。cache_write_tokens_details の ttl_30m_tokens / ttl_12h_tokens により、保持期間別の書き込みコストをモニタリングできる。

まとめ

Responses API に 12 時間のプロンプトキャッシュ保持期間が追加され、prompt_cache_options.ttl (または prompt_cache_breakpoint.ttl) に "12h" を指定することで利用できるようになった。書き込みコストは入力単価の 2.5 倍 (30 分保持は 1.25 倍)、読み取りは保持期間に関係なく 0.1 倍。対象は GPT-5.6 以降のモデルで、12 時間保持は Responses API のみの提供となる。長い間隔を挟んで再利用される安定プレフィックスに適用することで、間欠的なワークロードのコストを効果的に削減できる。
