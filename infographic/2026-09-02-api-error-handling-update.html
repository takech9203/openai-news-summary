概要

2026 年 9 月 2 日、OpenAI API のエラーレスポンスが更新され、「急激なトラフィック増加」と「一時的なモデル過負荷」という 2 つの異なる状況を、アプリケーション側で区別できるようになりました。

🔀

2 つのエラー状況を明確に区別

急激なトラフィック増加は HTTP 429 (エラーコード slow_down)、一時的なモデル過負荷は HTTP 503 (エラーコード server_is_overloaded) として返されます。

🎯

原因に応じたリトライ戦略の選択が可能に

開発者はエラーの原因 (クライアント側のトラフィック増加ペース or サーバー側の過負荷) に応じて、適切なリトライ戦略を選択できるようになります。

⏱️

Retry-After ヘッダーを優先

どちらのレスポンスにも Retry-After ヘッダーが含まれる場合があり、ヘッダーがある場合は指定された時間以上待機してからリトライすることが推奨されています。

📈

ヘッダーがなければ指数バックオフ

Retry-After ヘッダーがない場合は、指数バックオフ (exponential backoff) でリトライすることが推奨されています。

🛠️

公式 SDK は Retry-After をすでに考慮

公式 SDK は、リトライ対象のエラーに対して Retry-After ヘッダーをすでに考慮して動作します。

Before / After — エラーレスポンスの変更

❌ Before (変更前)

「クライアント側のトラフィック増加ペースの問題」と「サーバー側の一時的な過負荷」を区別しにくく、原因の切り分けが困難でした。

  • エラーの原因がクライアント側かサーバー側か判別しづらい
  • 原因別のリトライ戦略を選択できない

✅ After (変更後)

ステータスコードとエラーコードで原因を明確に判別できます。

  • 429 + slow_down: 急激なトラフィック増加
  • 503 + server_is_overloaded: 一時的なモデル過負荷
  • 原因別に最適化されたエラーハンドリングを実装可能

主な内容 — 2 つのエラーコードの比較

HTTP 429

🚦 slow_down: 急激なトラフィック増加

リクエストレートがサービスの安全に処理できる速度を超えて増加した場合に返されます。

エラータイプrate_limit_error
エラーコードslow_down
原因増加ペースの速さ (クライアント側)
  • RPM (requests-per-minute) や TPM (tokens-per-minute) の制限内でも発生し得る点が特徴で、レート制限超過とは異なり「増加ペースの速さ」が原因
  • 目安: トラフィックが入力 100 万 TPM に達した後は、15 分ごとに 50% を超えない範囲で増やす
  • 推奨対応: リクエストレートを下げ、その後段階的に増やす
HTTP 503

🔥 server_is_overloaded: 一時的なモデル過負荷

リクエストしたモデルに、その時点でリクエストを処理する十分なキャパシティがない場合に返されます。

エラータイプservice_unavailable_error
エラーコードserver_is_overloaded
原因一時的な状態 (サーバー側)
  • クライアント側のトラフィックではなく、サーバー側の一時的な状態を示す
  • エラーが継続する場合は、ステータスページでインシデントが発生していないか確認することが推奨

推奨リトライ戦略

条件 推奨される対応
⏱️ Retry-After ヘッダーあり 指定された時間以上待機してからリトライ
📈 Retry-After ヘッダーなし ジッター付きの指数バックオフでリトライし、リトライ回数に上限を設ける
💡 公式 SDK は、リトライ対象のエラーに対して Retry-After ヘッダーをすでに考慮して動作します。

技術的な詳細 — エラーレスポンスの例

エラーレスポンスの error オブジェクトには type と code が含まれ、error.code を確認することで具体的な原因を特定できます。以下はドキュメントに記載されたフィールドに基づく例です。

JSON 429 (slow_down) の例 
{
  "error": {
    "message": "Your request rate increased faster than the service can safely handle. Reduce your request rate, then increase it gradually.",
    "type": "rate_limit_error",
    "code": "slow_down"
  }
}
JSON 503 (server_is_overloaded) の例 
{
  "error": {
    "message": "The requested model does not have enough capacity to process your request at the moment. Please retry later.",
    "type": "service_unavailable_error",
    "code": "server_is_overloaded"
  }
}

コードサンプル

Retry-After ヘッダーを優先し、ない場合はジッター付き指数バックオフでリトライする Python の実装例です。

Python Retry-After 優先 + ジッター付き指数バックオフの実装例 
import random
import time

from openai import OpenAI, APIStatusError

client = OpenAI(max_retries=0)  # SDK の自動リトライを無効化し、手動で制御する例

MAX_RETRIES = 5
BASE_DELAY = 1.0  # 秒


def create_response_with_retry(**kwargs):
    for attempt in range(MAX_RETRIES + 1):
        try:
            return client.chat.completions.create(**kwargs)
        except APIStatusError as e:
            # 429 (slow_down) と 503 (server_is_overloaded) のみリトライ対象
            if e.status_code not in (429, 503) or attempt == MAX_RETRIES:
                raise

            retry_after = e.response.headers.get("Retry-After")
            if retry_after is not None:
                # Retry-After ヘッダーがある場合: 指定時間以上待機
                delay = float(retry_after)
            else:
                # ヘッダーがない場合: ジッター付き指数バックオフ
                delay = BASE_DELAY * (2 ** attempt) + random.uniform(0, 1)

            error_code = getattr(e, "code", None)
            print(f"HTTP {e.status_code} (code={error_code}): {delay:.1f} 秒待機してリトライします")
            time.sleep(delay)


response = create_response_with_retry(
    model="gpt-4o",
    messages=[{"role": "user", "content": "Hello!"}],
)
print(response.choices[0].message.content)
📝 公式 SDK のデフォルトのリトライ機構は Retry-After ヘッダーをすでに考慮するため、多くのケースでは SDK の自動リトライをそのまま利用できます。

開発者への影響

🔍 エラー原因の切り分けが可能に

これまで区別しにくかった「クライアント側のトラフィック増加ペースの問題 (429 slow_down)」と「サーバー側の一時的な過負荷 (503 server_is_overloaded)」を、ステータスコードとエラーコードで明確に判別できます。

🔧 エラーハンドリングの見直し

error.code に基づいて分岐するエラーハンドリングを実装している場合、新しいコード (slow_down, server_is_overloaded) への対応を追加するとよいでしょう。

⚡ リトライ戦略の最適化

429 (slow_down) ではリクエストレートを下げて段階的に増やす対応、503 (server_is_overloaded) では待機後のリトライとステータスページの確認という、原因別の対応が可能になります。

⏱️ Retry-After ヘッダーの活用

自前のリトライ処理を実装している場合は、Retry-After ヘッダーを優先し、ない場合のみ指数バックオフを使う実装が推奨されます。公式 SDK を利用している場合はヘッダーがすでに考慮されます。

ユースケース

🚀 トラフィックを段階的に拡大するアプリケーション

429 (slow_down) は RPM や TPM の制限内でも発生し得るため、急拡大するサービスではリクエストレートを段階的に増やす制御が有効です。公式ドキュメントでは、入力 100 万 TPM 到達後は 15 分ごとに 50% を超えない範囲で増やすことが目安とされています。

🛡️ 自前のリトライ処理を実装しているシステム

Retry-After ヘッダーがあれば指定時間以上待機し、なければジッター付き指数バックオフ (リトライ回数に上限を設定) でリトライする実装に更新することで、公式推奨に沿ったエラーハンドリングを実現できます。

📊 運用監視・アラートの高度化

503 (server_is_overloaded) はサーバー側の一時的な状態を示すため、エラーが継続する場合はステータスページでインシデントの有無を確認するフローを運用に組み込むことで、原因の切り分けが迅速になります。

まとめ

2026 年 9 月 2 日の更新により、OpenAI API は「急激なトラフィック増加 (429 slow_down)」と「一時的なモデル過負荷 (503 server_is_overloaded)」を明確に区別して返すようになりました。開発者は Retry-After ヘッダーがあれば指定時間以上待機し、なければジッター付き指数バックオフでリトライするという公式推奨に沿って、原因別に最適化されたエラーハンドリングを実装できます。
