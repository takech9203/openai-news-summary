Codex サンドボックスの内部構造

OS ネイティブ機構によるファイルシステム・ネットワーク制限の実装 — VM でもコンテナでもない、ユーザー環境内での多層防御

📅 2026-11-18 | OpenAI News (Engineering)

概要

OpenAI は、Codex がユーザーのマシン上でコマンドを実行する際にファイルシステム・ネットワーク制限をどのように強制しているかを解説する技術記事を公開した。開発者のラップトップは iOS ビルドツールチェーンや iPhone シミュレータなど Docker では再現できないホスト依存ツールを含むため、VM / コンテナではなく OS ネイティブのサンドボックス機構を採用している。

🛡️

OS ネイティブサンドボックスによる多層防御

モデルの訓練・アラインメントに加え、ハーネス側でも保護を実装する「defense in depth」の思想。macOS Seatbelt、Linux bubblewrap + seccomp-bpf、Windows MXC を採用し、ユーザーの既存環境内でコマンドを制約する。

📁

:workspace プロファイルがデフォルト

ワークスペース内の書き込み許可 (.git / .codex は読み取り専用)、広範なファイルシステム読み取り許可、ネットワーク無効化の 3 点を柱とする。

⚙️

config.toml でカスタムプロファイル定義

[permissions] セクションで read / write / deny のルールを定義。既存プロファイルの継承 (extends) や管理者向け requirements.toml による強制も可能。

🌐

codex-network-proxy でドメイン単位の制御

HTTP / SOCKS5 プロキシがドメインルール (allow / deny / 承認保留) を適用。ホスト名は許可または承認後にのみ解決し、DNS 漏洩を防止する。

📦

codex sandbox コマンドで MCP サーバーも保護

任意のコマンドをプロファイルの下で実行可能。デフォルトでは制約されない stdio MCP サーバーもラップして制限下で起動できる。

:workspace プロファイルの 3 つの柱

1

ワークスペース内の書き込みを許可: ただし .git や .codex は読み取り専用とし、.codex/config.toml や .git/hooks の直接改変を防止

2

広範なファイルシステム読み取りを許可: コンパイラやビルドツールがリポジトリ外の SDK やライブラリに依存するため。トレードオフとして API キーを含む設定ファイルなども読める可能性がある

3

ネットワークアクセスを無効化: データ流出や外部アップロードを防止。依存関係のダウンロードなど正当な操作にも追加許可が必要になる

⚠️ 残存リスクの例 node_modules/prettier のようなローカルパッケージへの悪意あるコード注入。node_modules は Git に無視されることが多く git status に現れないため、エディタの保存時フォーマッタ経由でサンドボックス外で実行され得る。

主要機能

🔧 共通サンドボックス API

spawn_command_under_sandbox() がコマンドと permission profile (限定的なネットワーク許可時はプロキシも) を受け取り、OS 固有実装が制約を適用。子プロセスは親の制約を継承し、プロセスツリー全体に適用される。

🎚️ exec_command の権限エスカレーション

モデルはコマンド単位で use_default / with_additional_permissions / require_escalated を指定可能。エスカレーション要求はユーザープロンプトまたは auto-review で処理される。

📝 プロファイルのカスタマイズと継承

extends = ":workspace" で組み込みプロファイルを拡張。:workspace_roots テーブルでワークスペースルート相対のルールを定義できる。複数の config.toml は階層的にマージ (テーブルは再帰マージ、配列は全体置換)。

🏢 管理者向けガードレール

requirements.toml と allowed_permission_profiles で利用可能なプロファイルを制約。":danger-full-access" = false のような明示的な禁止は上書き不可。クラウド配布の要件は /etc/codex/requirements.toml に優先する。

🔒 DNS 漏洩対策付きプロキシ

HTTP_PROXY / HTTPS_PROXY / ALL_PROXY に加え PIP_PROXY などアプリ固有の環境変数も注入。環境変数を無視するプログラムの直接接続は OS サンドボックスが遮断。ホスト名の解決は許可・承認後のみ。

技術詳細: サンドボックス API と設定

🔌 サンドボックス API と exec_command ツール

def spawn_command_under_sandbox(

🗂️ カスタムプロファイルの定義 (config.toml)

ファイルシステムエントリは read / write / deny の 3 種類。CLI は作業ディレクトリを唯一のワークスペースルートとし、ChatGPT デスクトップアプリはプロジェクトのソースフォルダを使用する。

TOML config.toml — カスタムプロファイル dev の定義 
# Use the dev profile by default.
default_permissions = "dev"

[permissions.dev]
# This is displayed when /permissions is run in the Codex CLI.
description = "Development with extra read-only protections."

# A profile can be derived from an existing profile.
# Profiles starting with ":" are provided by Codex.
extends = ":workspace"

[permissions.dev.filesystem]
"~/build-cache" = "write"

[permissions.dev.filesystem.":workspace_roots"]
".devcontainer" = "read"
".vscode" = "read"
"**/*.env" = "deny"
"secrets" = "deny"
TOML 組み込み :workspace プロファイルの保護 (参考) 
[permissions.":workspace".filesystem.":workspace_roots"]
".agents" = "read"
".aws" = "read"
".codex" = "read"
".git" = "read"
TOML requirements.toml — 管理者によるプロファイル制約 
default_permissions = ":read-only"

[allowed_permission_profiles]
":read-only" = true
":danger-full-access" = false

🌐 ネットワーク設定とドメインルール

ネットワークには「全ネットワーク無効 (:workspace のデフォルト)」「完全な直接アクセス (:danger-full-access のデフォルト)」「プロキシ経由に制限」の 3 オプションがある。ドメインルールは完全一致とワイルドカードをサポートし、明示的な deny が allow に優先する。

TOML config.toml — ドメインルールとプロキシの有効化 
[permissions.dev.network]
enabled = true

[permissions.dev.network.domains]
"*.openai.com" = "allow"
# Allow requests to local services by hostname or by IPv4/IPv6 loopback address.
"localhost" = "allow"
"127.0.0.1" = "allow"
"::1" = "allow"
"evil.example" = "deny"

[features]
# If neither local config nor managed requirements enable the proxy,
# this profile allows direct network access; domain rules are not enforced.
network_proxy = true
⚠️ DNS 漏洩に関する注意 プロキシは許可または承認後にのみホスト名を解決するが、広範なワイルドカードや DNS サービスへのアクセスを許可すると DNS ベースの情報流出が可能になる。

🧪 codex sandbox コマンドと MCP サーバーの保護

codex sandbox は任意のコマンドをプロファイルの下で実行でき、プロファイルのテストに利用できる。デフォルトで cwd をワークスペースルートとして扱う。

Console プロファイルの動作テスト 
$ codex sandbox --permission-profile dev -- \
    bash -c 'cat > .vscode/settings.json'
bash: .vscode/settings.json: Operation not permitted
TOML stdio MCP サーバーのサンドボックス化 
[permissions.memory-mcp.filesystem]
# Allow broad reads for Node.js/npm dependencies and configuration.
":root" = "read"
"~/.npm" = "write"
"~/mcp-data" = "write"

[permissions.memory-mcp.network]
enabled = false

[mcp_servers.memory]
command = "codex"
args = [
  "sandbox",
  "--permission-profile",
  "memory-mcp",
  "--",
  "npx",
  "--offline",
  "@modelcontextprotocol/server-memory@1.0.0"
]

[mcp_servers.memory.env]
MEMORY_FILE_PATH = "~/mcp-data/memory.jsonl"
Bash 事前準備 — npm キャッシュへのパッケージ投入 
# The sandbox can write to this folder, but it cannot create it.
mkdir -p ~/mcp-data

# Installing the MCP server requires network access.
npx -y --package=@modelcontextprotocol/server-memory@1.0.0 -c true

技術詳細: OS 別サンドボックス実装

🍎

macOSSeatbelt (sandbox-exec + SBPL)

Apple のカーネル強制サンドボックス機構 Seatbelt を /usr/bin/sandbox-exec 経由で使用。ポリシーは Scheme ベースの SBPL (Sandbox Profile Language) で記述する。

Scheme SBPL — /dev/null と /dev/zero の読み書き許可 
(allow file-read* file-test-existence file-write-data
  (literal "/dev/null")
  (literal "/dev/zero"))
  • ベースプロファイルは (deny default) で開始し、明示的に許可した以外のアウトバウンド接続を遮断
  • プロキシ有効時はローカルポート (例: localhost:3128、localhost:8081) への接続許可ルールを注入
  • (param) プレースホルダと -Dkey=value オプションで値を埋め込める
  • SBPL は非公開かつ man sandbox-exec に DEPRECATED 表記があるが、macOS はプロファイルを同梱し続けており Chrome / Chromium も依存しているため、当面 Seatbelt を継続使用する方針
🐧

Linuxbubblewrap + seccomp-bpf

codex-linux-sandbox ヘルパーが bwrap でマウント名前空間内のファイルシステムビューを構築し、その中で seccomp-bpf を適用してからユーザーコマンドを実行する。

Shell 起動構造 
bwrap BWRAP_ARGS... -- \
  codex-linux-sandbox --apply-seccomp-then-exec CODEX_LINUX_SANDBOX_ARGS... -- \
  PROG ARGS...
  • bwrap は自前のベンダー版を同梱するが、PATH 上の互換インストールを優先 (一部ディストリビューションがユーザー名前空間を無効化しつつシステム bwrap に例外を与えるため)
  • --bind (書き込み可) / --ro-bind (読み取り専用) でパスを公開し、--perms 000 --tmpfs などでディレクトリ・ファイルを拒否
  • --unshare-ipc、--unshare-pid で他リソースも隔離し、ネットワーク無効時またはプロキシ使用時は --unshare-net で新しいネットワーク名前空間を作成
  • deny グロブは起動前に具体パスへ展開 (実行中に新たに一致するパスは追加されない)
  • seccompiler crate で BPF プログラムを動的コンパイルし、プロセスツリー全体に継承。no_new_privs フラグで setuid 実行による権限昇格も防止
  • ネットワーク無効時は connect(2)、bind(2) などを遮断。プロキシ有効時は IP ソケットを許可しつつ、スタンドアロン Unix ドメインソケットの作成をデフォルトで遮断
  • プロキシ接続は FD ハンドオフ方式: サンドボックス内で作成したループバック TCP リスナーの FD を Unix ソケットペア経由でホスト側プロセスへ引き渡し、ホストのネットワーク名前空間を晒さずに中継する
🪟

WindowsMXC (Microsoft eXecution Container)

従来の自前サンドボックス (管理者権限が必要、ACL 操作が高コスト、ホストに永続状態が残る) から、Microsoft の MXC ベース実装へ移行中。MXC は JSON 設定スキーマを公開しており、Codex は mxc-sdk crate で実行リクエストを構築する。

JSON MXC 設定の例 (ファイルシステム + ネットワーク) 
{
  "filesystem": {
    "readwritePaths": [
      "C:\\work\\demo",
      "D:\\Users\\dev\\build-cache"
    ],
    "readonlyPaths": [
      "C:\\",
      "D:\\",
      "Z:\\",
      "C:\\work\\demo\\.agents",
      "C:\\work\\demo\\.aws",
      "C:\\work\\demo\\.codex",
      "C:\\work\\demo\\.devcontainer",
      "C:\\work\\demo\\.git",
      "C:\\work\\demo\\.vscode"
    ],
    "deniedPaths": [
      "C:\\work\\demo\\config\\dev.env",
      "C:\\work\\demo\\config\\prod.env",
      "C:\\work\\demo\\secrets"
    ]
  },
  "network": {
    "egress": {
      "default": "deny",
      "allow": [{
        "to": [
          {"cidr": "127.0.0.0/8"},
          {"cidr": "::1/128"}
        ]
      }]
    },
    "ingress": {
      "default": "deny",
      "hostLoopback": "allow"
    }
  }
}
  • 固定設定: レジストリ読み取りと PowerShell 起動に必要な Win32k / デスクトップアクセスを保持しつつ、クリップボード、入力注入、デスクトップ / システム設定の制御は無効化。ホストのファイルシステム権限改変へのフォールバックも禁止
  • ドライブルート: MXC はデフォルト拒否のため、広範な読み取りを実現するためにローカルドライブルートへ読み取り専用グラントを再帰的に追加
  • 競合解決: より具体的なパスが祖先のグラントを上書き。エイリアス / シンボリックリンク / ジャンクションが同一パスを指す場合は厳しい方が優先 (deny > read-only > read-write)
  • ネットワーク: 直接の外部接続を遮断しつつホストループバック接続 (プロキシを含む) を許可し、ドメインルールは共有プロキシが外部で強制

ユースケース

🗂️ プロジェクトに合わせた権限設計

:workspace を extends で継承し、**/*.env や secrets の deny、~/build-cache への write 追加など、プロジェクト固有の要件に合わせたカスタムプロファイルを定義。codex sandbox コマンドで事前に動作を検証できる。

🔌 stdio MCP サーバーのサンドボックス化

ハーネスは MCP サーバーの起動コマンドをデフォルトではサンドボックス化しないが、codex sandbox でラップすることで制約下で実行できる。npm キャッシュへ事前にパッケージを投入すれば、npx --offline によりネットワーク無効のまま起動可能。

🏢 組織ポリシーの強制

管理者は requirements.toml で利用可能なプロファイルを制約し、:danger-full-access の禁止など上書き不可能なガードレールを組織全体に配布できる。クラウド配布の要件は /etc/codex/requirements.toml に優先する。

開発者への影響

🔍 サンドボックス挙動の透明性向上: Codex がローカル環境で何を許可し何を遮断しているかが明確になり、エージェントにタスクを委任する際のリスク評価がしやすくなる
🎛️ カスタムプロファイルによる細かな制御: .env ファイルの deny やビルドキャッシュへの write 追加など、プロジェクトに合わせた権限設計ができる
🌐 ドメイン単位のネットワーク制御: 全面許可 / 全面禁止の二択ではなく、必要なドメインのみ許可する運用が可能になる
🛡️ MCP サーバーの保護: デフォルトでは制約されない stdio MCP サーバーにもファイルシステム・ネットワーク制限を適用できる
🏢 組織ポリシーの強制: 上書き不可能なガードレールを管理者が配布できる
⚠️ 残存リスクの認識: 広範な読み取り許可による秘密情報の読み取り、node_modules 経由のサンドボックス外コード実行、広いワイルドカード許可時の DNS ベース流出など、サンドボックスでも防げないリスクを理解した上で運用する必要がある

まとめ

Codex のサンドボックスは VM やコンテナではなく、OS ネイティブ機構 (macOS の Seatbelt、Linux の bubblewrap + seccomp-bpf、Windows の MXC) の上に構築されている。3 つの OS で共通のサンドボックス API と permission profile を通じて、ワークスペース書き込み許可・広範な読み取り・ネットワーク遮断というデフォルトを強制しつつ、config.toml によるカスタマイズ、codex-network-proxy によるドメイン単位の制御と DNS 漏洩対策、管理者向けの requirements.toml まで多層的な制御を提供する。OpenAI は今後、権限設定の簡易化と OS 保護機構の活用拡大により、ユーザーの制御を保ったままエージェントの能力を広げることを目標としている。
